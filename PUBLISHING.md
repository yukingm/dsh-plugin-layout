# Publishing this plugin to the marketplace

The plugin is listed through
[awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin).
That repository generates its README from `data/plugins/*.yml`, so a submission
is **one YAML file**, not a README edit. This checklist maps this folder onto
[contributing.md](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/contributing.md)
and lists the placeholders that must be filled first.

## 1. Fill the placeholders

The package uses the GitHub owner `yukingm` wherever an owner is needed:

- `package.json`: `repository.url`, `bugs.url`, `homepage`, `author`.
- `LICENSE`: replace `dsh-plugin-layout contributors` if you want your name.
- `awesome-entry.yml`: `url`, `name`, `icon`.

Keep the three package.json URLs pointed at the repository that will be listed;
if the package is also published to npm, the registry page must lead back to the
same repository.

## 2. Create the repository

The repository is the unit that gets listed, so it has to satisfy the hard
requirements before the PR:

- [ ] Push this folder as its own repository (root `package.json` - a subpackage
      would need a `#subname` entry and a `owner__repo--packages-x.yml` name).
- [ ] Add the `dsh-plugin` topic to the repository (GitHub rejects the entry
      without it).
- [ ] The repository must be at least one day old when the PR is reviewed.
- [ ] `package.json` declares `dsh.bundle.patch` pointing at a real
      `cordis.patch.yml`; `dsh.client` alone is not installable and is the most
      common rejection reason. `node test/manifest.mjs` checks this.
- [ ] The description is one line, accurate, ends with a period, and is not
      marketing copy - reviewers compare it with the code.

## 3. Verify locally

```bash
node --check index.js && node --check client.js
node test/harness.mjs
node test/manifest.mjs
```

`test/manifest.mjs` mirrors the CI's first gate: the `dsh.bundle` manifest, the
patch file, the locale files, the raster tile, and the `files` list.

## 4. Add the entry file to awesome-dsh-plugin

Copy `awesome-entry.yml` to
`data/plugins/yukingm__dsh-plugin-layout.yml` (the separator is two
underscores, and the file name must match the repository). The entry fields:

```yaml
url: https://github.com/yukingm/dsh-plugin-layout
name: yukingm/dsh-plugin-layout
category: ui
description:
  en: Hide, show, and reorder the entries other plugins register into the DeepSeek Harness sidebar, session header, and settings.
  zh: 扫描插件在侧栏、标题栏、设置里挂的入口, 逐条隐藏、显示或排序。
icon: https://raw.githubusercontent.com/yukingm/dsh-plugin-layout/main/assets/icon-180.png
```

`category: ui` is the closest fit; maintainers re-file entries rather than reject
them. Valid categories are agi, ui, usage, theme, model, identity, session,
memory, tools, wsl, browser, vision, voice, docs, skill, workflow, git, notify,
dev, security, remote, market, fun.

`icon` must be a GitHub-hosted raster image (png, jpg, jpeg, webp; SVG and other
hosts are refused). `assets/icon-180.png` is generated by
`scripts/make-icons.py` and drawn at roughly 96px on the storefront, so keep the
shapes readable at that size.

One PR may add at most three entries. Never edit the generated README: CI
rebuilds it from the YAML.

## 5. Optional extras

- **npm**: `npm publish` after replacing `OWNER` - the list does not require npm,
  but if you publish, `repository` must point back at the listed repository, and
  any `@deepseek-ai/*` package must be a `peerDependency` with an explicit
  prerelease range such as `">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0"`
  (a broad range silently excludes e.g. `0.1.0-rc.6`).
- **screenshots.json** next to `package.json`: 1-8 paths relative to the
  repository root, no leading `/` and no `..`, e.g.
  `{"screenshots": ["assets/screenshot-settings.png"]}`. The storefront falls
  back to images that appear in the README, so nothing breaks without real
  screenshots - but take at least one of the settings page before submitting.
- **tarball**: an `https` `.tgz` hosted on GitHub releases, if you want an
  offline install path. `latest/download/` requires an asset name without a
  version in it.

## 6. What CI checks

In order: entry count, `dsh.bundle` fetch (root of the repository),
repository age, `awesome-lint`, then the site build (locale parity, separators,
dates, screenshots). If the PR gets the `held: author` label, push fixes to the
same branch instead of opening a new PR, and leave one comment.

## 7. Release checklist

- [ ] `version` bumped in `package.json` and a matching `CHANGELOG.md` heading
- [ ] `node test/harness.mjs` and `node test/manifest.mjs` pass
- [ ] installed copy in the DSH profile updated and the desktop app restarted
- [ ] `git tag v<version>` and a GitHub release if a tarball is offered
- [ ] entry YAML still matches the repository name and description
